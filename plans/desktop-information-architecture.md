# CtxFerry desktop information architecture

**Functional specification for the desktop redesign.** A developer opening CtxFerry usually has one of three questions: “What needs attention on this device?”, “What does this Project use here?”, or “What will travel to another device?” Home, Projects and Sync own those questions. Tools used across Projects have one shared home in Catalog. The following names describe destinations and actions. They can be localized independently of stored identifiers.

## Product boundary and ownership

The desktop opens the same Workspace as the CLI. A Workspace contains shared Project definitions and this device's local catalog. A Checkout binds a local directory to a Project. Multiple Checkouts can share a Project while using different Profiles. A Task belongs to a Project and declares resource and credential requirements. A Resource describes an endpoint's purpose. An execution environment supplies route and availability evidence. A credential binding names a provider entry. Its secret value stays with the provider.

| Object | Shared information | Evidence or choice on this device |
| --- | --- | --- |
| Project and Checkout | Identity, Profiles, shared configuration, context and Tasks | Project subscription, directory binding, selected Profile, overrides and execution trust |
| Resource and credential | Resource definition and credential reference mapping | Local route, probe result, provider session and entry check |
| Skill | Approved source and pin for shared Skills | Target, installed version, file drift and installation receipt |
| Run and artifact | Eligible run records, artifact metadata and eligible bytes | Completion evidence and available bytes can differ by device |
| Sync record | Revision eligible for exchange with the private repository | Queue, conflicting revisions, checked remote evidence and backup destination |

A preview describes a possible effect. A receipt describes a completed operation with its target, scope and outcome. A local write to a shared record can still be awaiting publication. Only confirmed sync evidence establishes publication.

## Destination map and movement

| Primary destination | Children in reading order | Starting scope |
| --- | --- | --- |
| Home | Device summary, attention items, bound Projects | Current Workspace and device |
| Projects | Project list → Project overview → Configuration, Context, Tasks, related resources, credentials, Skills and artifacts | Explicit Project, then local Checkout where relevant |
| Catalog | Resources & environments, Credential bindings, Skills, Run artifacts | Choose Project for scoped collections. Skills also supports the device catalog |
| Sync | Repository, Queue → Record → Conflict resolution, Backup | Workspace, with optional queue filter |

Catalog is a directory of four tools. Each entry states what the operator can do there. Project links open the same tool with the relevant IDs supplied. “Back” restores the calling Project, Checkout, section and selection. Direct entry from Catalog has Catalog as its parent. Keep a stack of origin routes, including links between Catalog tools. Opening another primary destination deliberately starts at its root. Reselecting Sync inside a conflict returns to the originating queue and restores its filter and selection. While a confirmed write is in progress, retain its target and block navigation while the operation is running. After interruption or loss of acknowledgement, show “outcome unknown”, reread durable state and reconcile before enabling retry. An unavailable object yields its parent collection and an explanation. Never substitute another writable target silently.

Use IDs for Workspace, Project, Checkout, Profile, Task, slot, environment, run and selected record as applicable. Labels and filesystem paths are presentation data except where the core explicitly requires a path. Explicit navigation scope takes precedence over remembered filters. A parent change clears invalid child selections, drafts, confirmations and receipts. An asynchronous result belongs to the scope that started it. Prompt to keep editing or discard unsaved input before leaving. Returning from a completed action reloads affected records and preserves surviving selection and filters.

## View contracts

Each row describes a user-visible destination or a step nested inside one. Actions that hand off to the CLI show the data root, prerequisites, command and how to refresh after completion.

| View | What the user needs to know | Actions, result and recovery |
| --- | --- | --- |
| Workspace readiness | Shell-level gate above all destinations. Show data root, initial loading state, catalog compatibility and last successful local read | For a fresh root offer create or join. For an older catalog migrate using a matching CLI. For a newer schema update CtxFerry. For an unreadable catalog run `ctxferry doctor`. After a failed refresh retain the last snapshot as stale, disable backup and remote check, and require a successful reread before a write. Refresh retries the same root. An initialized Workspace can proceed locally without a remote. |
| Home | Device identity, bound directories by Project, last confirmed sync, service state, separate waiting, conflict and blocked-only counts | Open Project or any of the three filtered queues with matching scope. Refresh rereads local evidence. An empty Workspace offers the binding handoff. |
| Project list and overview | Project identity, device subscription, local bindings, available Checkouts and active Profile | Open a Project, choose a Checkout, explicitly change its saved Profile. Identify the affected Checkout before saving, report its saved Profile, reload Configuration and Context, and recompute Task trust. Explain unavailable directories. For an unsubscribed Project retain its ID, show identity and offer `ctxferry project subscribe`. Catalog pickers list subscribed Projects. With none, link to Projects for subscription and keep device-wide Skills accessible. A subscribed Project without a usable Checkout can still expose shared records. |
| Configuration | Effective value, origin and ordered workspace-default, Project, Profile, device and Checkout contributions | Select field and writable layer. Edit or remove that layer's override. Preview affected local Checkouts, retained or inherited values and publication scope. Confirm, reload and verify the effective result. |
| Context | Project subscription, Checkout, effective Profile, document origin, content availability and pagination | Keep the same Checkout and resolved Profile for listing, opening a document and loading more. Explain an unsubscribed Project before querying. Select document, read available content, return to the same collection. Describe missing content or read failures separately from an empty result. |
| Tasks | Purpose, inputs, resource slots, credential requirements and local execution definition | Open Task, inspect or recheck trust for the selected Checkout, resolve the slot through the selected Profile as described in journey 3. A changed definition identifies changed fields. Enabling trust and running a Task use the CLI. |
| Resources & environments | Selected Project, Resource, applicability, stage, configured endpoint, local override/proxy and per-environment observations | Select environment. For an applicable local route, review actual TCP host and port, confirm probe and read target-specific result. For another environment inspect timestamped observations. Unknown evidence stays unknown. |
| Credential bindings | Project, Profile, Task and requirement, expected type, mapped alias, locator and provider profile | Reuse a compatible reference or enter a new locator. Preview slot and alias, confirm shared mapping. Separately check local authentication, adopt configured provider session or check entry readability. Route sign-in and entry management to provider. Exclude values from drafts, results and copied commands. |
| Skills | Project or device catalog, Skill, target, applicability, approved pin, installed pin, source and ownership | Select install, update, previous-version rollback or interrupted-install recovery. For local Git packages choose a supported pin. Inspect candidate and per-file changes. Drift blocks confirmation until reconciled and rescanned. Receipt identifies actual local target and version. Shared pin approval uses the CLI. |
| Run artifacts | Project, run, source device, content state, size and digest. Show provenance and completion scope when available | Filter, open artifact and inspect metadata. Verify available bytes and export to a new file. Report verified destination or failure. A metadata-only item explains why content is absent and identifies its origin. |
| Sync repository | Remote configuration, branch, last confirmed commit, history size, service and latest check | Check reachability and privacy on demand. With no remote, guide private repository setup, export manifest review, separate plaintext source inspection and explicit first publication through the CLI. Offline, retain local work and identify last confirmed evidence. |
| Queue and record | Waiting, conflicted and blocked records, Project where known, kind, ID and revision evidence | Filter, inspect, open conflict or blocking reason, or follow the routine sync handoff below. Cleared selection after refresh explains that the record left the filter. Show an empty Workspace queue only when all three groups are empty. |
| Conflict resolution | Record identity, local and remote versions, deletion state and available comparison | Compare and keep either whole side, including deletion. Disclosure policy may hide fields on an existing side. Offer document replacement only for Context with a non-deleted side, retaining shared storage. Preview the result and confirm against the conflict token. Reconcile an uncertain push before retrying. On stale data reload and choose again. Receipt identifies the new local revision pending publication. Return to originating queue. |
| Backup | Workspace, absolute new directory, optional local-only data and plaintext exposure | Ordinary queued edits allow backup. An uncertain publication journal blocks backup. Open Repository and follow the recovery action for that journal below. Review scope and confirm write. Show destination and manifest on success. Reject an existing target and allow another destination. Restore follows the recovery guide through the CLI. |

### Routine sync and blocked work

Before the first confirmed commit, Repository owns first publication. With no pending journal, use the review and confirmation steps in journey 1. If the first push lost its acknowledgement, offer **Resume first publication** on the same data root. Recover the original preview ID associated with the pending initialization journal and show `ctxferry sync init --preview <originalPreviewId>`. Reuse the reviewed ID for this attempt. A newly generated ID cannot reconcile the journal. Return to Repository and reread the confirmed commit and journal before unlocking Backup or Conflict.

Once a confirmed commit exists, both Repository and Queue offer **Sync via CLI** for the displayed data root. With a configured private remote, credentials and connectivity, run `ctxferry sync` against that root. A running service normally processes eligible records automatically. Show its reported state and last confirmed commit. When the service is stopped or absent, the same command provides a one-shot cycle. Offline, keep the queue inspectable and offer the handoff on reconnect. For an uncertain routine push, offer **Reconcile publication** using the same one-shot command. Backup and Conflict link to the matching recovery action in Repository. On return, refresh the local snapshot, confirmed commit, journal state and queue before offering another write.

Group records by stable record ID. A conflicted record opens comparison. A blocked record without its own conflict shows the core's reason and related IDs where available. Waiting means pending with neither flag. Count each ID once in that order. A dependent record links to its blocking conflict when known. For a uniqueness collision, identify the affected Project or record and direct the operator to correct the colliding definition. Keep other reason codes available for diagnosis. After a repair, run sync and refresh to discover whether the unit can publish.

## Journeys and decision points

1. **Bring a device online.** Choose the intended Workspace before initializing the data root.
   - **Create a Workspace.** Initialize locally, then bind a directory to create the first Project. Local work can begin here. To publish, configure a private repository with `ctxferry sync enable` and require the privacy check to return `enabled`. Inspect paths, sizes and SHA-256 digests in `ctxferry sync preview --format json`. Separately read the original shared documents and artifact payloads for sensitive plaintext. Confirm the reviewed bytes with `ctxferry sync init --preview <previewId>` and refresh.
   - **Join an existing Workspace.** From a fresh data root use `ctxferry join` with the existing private repository. Choose subscriptions explicitly with `--subscribe` or `--all-projects`, or subscribe later. Bind the local directory with `ctxferry project bind . --project <id>` so it uses the existing Project. Refresh and open the new Checkout. An already initialized root must be preserved when selecting a fresh join destination.
2. **Explain a surprising value.** Home → Project → affected Checkout → Configuration → inspect winning layer → preview reset of that override. If another Checkout would change, return to layer selection. Confirm the intended scope → check effective value and origin → inspect pending records for a shared write.
3. **Prepare a Task.** Project → Checkout → Task → review execution definition → look up (Task ID, slot name) in the saved Profile → open that Resource ID in the current environment → compare local route with remote observations → probe the local endpoint → Back → follow credential requirement → map compatible reference if missing → check session then entry. Return to the same Task. If the Profile lacks the mapping, offer `ctxferry profile map-resource` and refresh before enabling the probe. Open credential management with Project, Profile, Task and requirement. Require the binding to match the mapped Resource. A mapping or binding change requires a fresh trust check. A successful probe, readable entry and execution trust are three separate findings.
4. **Reconcile two devices.** Home conflict count → filtered Queue → record comparison → choose a whole side or replace eligible Context → review deletion or replacement → confirm. If the revision changed, reread both sides. If saved, return to the refreshed queue and follow the routine sync handoff and refresh the affected records.
5. **Adopt a Skill update.** Project → related Skills → target → approved candidate → inspect file diff. If local edits conflict, reconcile files, rescan, review and confirm. Check the installed receipt. To undo, preview the available previous version and confirm its local effects.
6. **Retrieve run evidence.** Project → related artifacts → filter by run and source → inspect digest and content availability. For available bytes choose a new destination, verify and export. For metadata-only records use source identity to locate the original. Back restores the initiating Project.
7. **Take a backup while offline.** With a readable local catalog, open Sync → Backup. If a push has an uncertain outcome, preserve local work, keep Backup blocked while offline, then reconnect and follow the matching recovery action in Repository before retrying. Otherwise choose new directory and data scope → review plaintext contents → confirm → locate manifest. Reopening Sync preserves the last confirmed remote evidence.

## Acceptance before visual design

- Start with a fresh data root and complete local setup without a remote. Repeat with a catalog requiring migration. Also open a newer schema and simulate refresh failure after a successful read. Verify the distinct recovery actions and stale-snapshot restrictions. Join an existing private Workspace on a second device, subscribe and bind by Project ID.
- Use two Projects with identically named Tasks, two Checkouts of one Project and different Profiles. Follow links into each Catalog tool and return. Read a Context document and its next list page under each Profile. Test Task → Credential bindings → Resources and Back twice. Open an unsubscribed Project directly, subscribe and recover the original selection. Every action, receipt and Back destination identifies the intended scope.
- Change scope while a read is pending. The previous result cannot become the current evidence. Change a revision or a Skill file after preview. A stale confirmation cannot write.
- Visit an empty collection, a filter with no matches, an unavailable local directory and a failed read. Distinguish the four outcomes and offer the corresponding add/bind handoff, clear filter, select Checkout or retry action.
- Inspect a remote environment, an unauthenticated provider, a metadata-only artifact and a deleted conflict side. Each view identifies exactly what can be inspected and which operation requires more evidence.
- Exercise a queue with only blocked records, a conflict holding a dependent record and a stopped service with ordinary waiting records. Follow each handoff and verify counts, reasons and the last confirmed publication after refresh.
- Lose acknowledgement once during first publication and once during routine sync. From Backup, recover the first using its original preview ID and the second using one-shot sync. Verify the journal clears and the confirmed commit is reread before retrying Backup.
- Cancel every preview before confirmation. Check that no mutation occurred. For failed or interrupted writes, reread the actual state before offering retry. Successful local operations expose their scope independently of publication.
